# 缓存与 CDN 加速 设置

> 适用版本：v1.3.0 及以上（含缓存链路两处修复）
> 控制台路径：`#/waf/cache`
> 最后更新：2026-11-16

---

## 一、能力定位

这是 WAF 内置的**边缘缓存层**，形态接近 CDN 的「静态资源加速」：把可缓存的响应收进进程内存，回源时按客户端能力重新协商 `br` / `gzip`，图片可按需转 WebP。

| 与公网 CDN 的相同点 | 与公网 CDN 的差异 |
|---|---|
| 内存缓存 + TTL + LRU 淘汰 | 缓存数据在**单机进程内**，重启即清空，不跨节点共享 |
| 按路径规则匹配（后缀 / 前缀 / 正则等） | 缓存键含 **站点 + Host + 路径 + Query**，天然按站点隔离 |
| 协商压缩、图片格式转换 | 没有「边缘节点回源合并」，也没有预热与持久化 |
| 命中打标（`X-Cache: HIT`、`Age`） | 容量以「进程内存」为上限，需自行估算 |

它适合：静态资源（js / css / 图片 / 字体）、可公开的 HTML、站点公告类页面。
不适合：登录态响应、个性化接口、任何带 `Set-Cookie` 的内容。

---

## 二、处理链路

| 阶段 | 行为 |
|---|---|
| 策略提前判定 | 拒绝类策略先执行（详见《精准访问控制 设置》第 6.4 步） |
| 规则匹配 | 按 `priority ASC, id ASC` 取**第一条命中**的缓存规则 |
| 缓存查找 | 命中且未过期 → 直接返回，记 `X-Cache: HIT`、`Age: 秒数`，回源次数为 0 |
| 未命中 | 正常回源，响应经「加速 writer」缓冲 |
| 缓冲期写入 | 状态码 200、体积未超限、响应头允许 → 写入缓存；同时按客户端 `Accept-Encoding` 压缩、按 `Accept` 转 WebP |
| 超限降级 | 体积超过单对象上限或超过 300 ms 宽限期 → 边收边发，不缓存 |

只有**匿名 GET / HEAD** 参与缓存：带 `Cookie`、带 `Authorization`、带 `Range`（断点续传）的请求一律不查缓存。

## 三、全局设置（全局设置页签）

| 设置项 | 含义 | 默认值 | 建议 |
|---|---|---|---|
| 启用 | 总开关。关闭后**所有规则停止命中，压缩与 WebP 一并停用** | 关 | 先配规则再开 |
| Gzip 压缩 | 对可压缩类型做 gzip | 开 | 保持开 |
| Brotli 压缩 | 对支持的客户端用 brotli（优先于 gzip） | 开 | 保持开 |
| WebP 转换 | 把 JPEG / PNG 按需转 WebP，仅对 `Accept` 含 `image/webp` 的客户端 | 关 | 图片站可开，注意 CPU |
| 默认缓存时长 | 规则里未填 TTL 时的兜底 | 300 秒 | 与规则一起规划 |
| 压缩最小字节 | 小于该体积不压缩（收益低） | 1024 B | 保持默认 |
| 缓存总容量 | 所有缓存对象的字节上限，超出按 LRU 淘汰 | 128 MiB | 按内存余量给，别超过可用内存的一半 |
| 单对象上限 | 单个响应可入缓存的最大字节数 | 2 MiB | 有大型 bundle 时调到 8–10 MiB |

> 单对象上限没调够，大 bundle 会**连压缩都不做**直接透传（体积判定先于压缩），表现为「规则配了但那个文件永远不命中」。用 `ls -lh` 确认源站文件大小后再定这个值。

## 四、缓存规则

### 4.1 字段

| 字段 | 说明 |
|---|---|
| 规则名称 | 便于识别，如「静态资源-CSS」 |
| 生效站点 | 留空 = 全部站点；填写时用**站点名称** |
| 匹配方式 | 六选一，见下表 |
| 匹配表达式 | 与匹配方式配套，见下表 |
| 缓存时长 | 秒。**硬过期**，到期即回源，没有 stale-while-revalidate |
| 优先级 | 数字小的先命中；同优先级按 ID |
| 启用 | 单条规则开关 |
| 备注 | 变更说明 |

### 4.2 六种匹配方式的真实语义

| 匹配方式 | 代码行为 | 表达式示例 | 陷阱 |
|---|---|---|---|
| **后缀匹配** | `strings.HasSuffix(path, pattern)`，**单值字面量** | `.css` | 写成 `.css,.js` 或 `*.css` **永远不会命中**——它不做列表也不做通配 |
| **精确匹配** | `path == pattern` | `/index.html` | 含 Query 的路径不相等，`/a?x=1` 不会命中 `/a` |
| **前缀匹配** | `strings.HasPrefix` | `/static/` | 会把该目录下图片、字体、HTML 一起缓存 |
| **正则匹配** | Go `MatchString`，**子串匹配** | `\.(css|js)$` | 必须写 `$`，否则 `/x.js.map` 也命中 |
| **目录匹配** | 等于该目录或以 `目录/` 开头 | `/blog` | 比前缀更安全，不会误伤 `/blogger` |
| **仅访客** | 仅对**无 Cookie / 无 Authorization** 的匿名请求生效，表达式限定路径前缀（空或 `*` 表示全部） | `/` 或 `*` | 防止把登录态页面缓存后发给游客 |

### 4.3 全站 CSS / JS 的两种配法

**方案 A：两条后缀规则（推荐）**

| 字段 | 规则 1 | 规则 2 |
|---|---|---|
| 规则名称 | 静态资源-CSS | 静态资源-JS |
| 生效站点 | 全部站点 | 全部站点 |
| 匹配方式 | 后缀匹配 | 后缀匹配 |
| 匹配表达式 | `.css` | `.js` |
| 缓存时长 | 86400（带内容指纹可设更长） | 86400 |
| 优先级 | 10 | 10 |

判定是 O(1) 字符串比较，语义清晰，出错面最小。

**方案 B：一条正则规则**

匹配方式选「正则匹配」，表达式：

```regex
\.(css|js)$
```

需大小写不敏感时写 `(?i)\.(css|js)$`。注意 `$` 不能省。

**不建议**用前缀匹配 `/static/` 兜全站：粒度失控，且资源分散在 `/assets/`、`/js/` 时要建多条。

## 五、哪些响应会被缓存

回源后逐项判定，任一不满足即不缓存（但压缩与 WebP 仍可能生效）：

| 判定项 | 条件 |
|---|---|
| 方法 | 仅 `GET` / `HEAD` |
| 状态码 | 仅 `200` |
| 请求头 | 无 `Range`；查询缓存时无 `Cookie`、无 `Authorization` |
| 响应头 `Set-Cookie` | 存在则不缓存 |
| 响应头 `Cache-Control` | 含 `no-store` / `private` / `no-cache` 则不缓存 |
| `X-Accel-Expires` | 为 `0` 则不缓存 |
| 体积 | 超过「单对象上限」不缓存，且直接透传 |
| 内容类型 | `text/event-stream`（SSE）必须立即透传，不缓存 |
| 上游编码 | `gzip` / `br` / `deflate` 先解码再缓存；其它编码整体透传 |

> 很多框架在开发模式给静态资源发 `no-cache`，这类必须在源站放开，否则规则永远命中不了。

## 六、压缩与 WebP

| 能力 | 触发条件 | 行为 |
|---|---|---|
| Brotli | 全局开 Brotli、内容类型可压缩、客户端 `Accept-Encoding` 含 `br` | 优先使用，比 gzip 再小 15–25% |
| Gzip | 客户端只接受 gzip | 兜底 |
| WebP | 全局开 WebP、类型为 JPEG/PNG、客户端 `Accept` 含 `image/webp` | 按需转码，失败回退原图 |

同一份缓存对象只存**原始字节**，压缩在响应时按客户端能力执行，因此 `br` / `gzip` / `identity` 三种客户端共用一条缓存，不会互相污染。

## 七、验证方法

```bash
# 首次请求（无 X-Cache），二次请求应命中
curl -sI https://goframe.phpframe.org/assets/index-DmplYGAM.js -H 'Accept-Encoding: br'
```

| 期望结果 | 含义 |
|---|---|
| `X-Cache: HIT` | 命中缓存 |
| `Age: 3` | 对象已在缓存中存活 3 秒 |
| `Content-Encoding: br` | 走了 brotli |
| 第二次耗时显著低于第一次 | 未回源 |

同一 URL 换编码再验：

```bash
curl -sI https://站点/assets/app.js -H 'Accept-Encoding: gzip'     # Content-Encoding: gzip
curl -sI https://站点/assets/app.js -H 'Accept-Encoding: identity' # 无编码，原始体积
```

三者都应 `HIT`，且体积依次递增。

## 八、发版与清缓存

TTL 是**硬过期**，没有 stale-while-revalidate。发版后两种处理：

| 场景 | 做法 |
|---|---|
| 文件名带内容指纹（`app.9f2c1.js`） | 无需处理，新文件名天然是新对象；TTL 可设 30 天 |
| 文件名固定（`app.js`） | 必须点「清空缓存」，或按「站点 + 路径前缀」精准清理 |

清缓存入口在规则页签顶部，可选填路径前缀（如 `/assets/`）。TTL 设得越长，发版越依赖手动清理——这是主要风险点。

## 九、与其它模块的执行顺序

| 顺序 | 模块 | 与缓存的关系 |
|---|---|---|
| 1 | IP 白名单 / 封禁 | 已封禁 IP 不会走到缓存 |
| 2 | Bot 检测 | 先于缓存，命中即拒 |
| 3 | 人机校验 | 先于缓存 |
| 4 | 限流 | 先于缓存，超频 429 |
| **5** | **策略提前判定** | **先于缓存**：拒绝类策略在此生效，避免缓存命中绕过拦截 |
| 6 | 缓存查找 | 命中直接返回 |
| 7 | 读 body → 完整策略 → 规则检测 → 回源 | — |

## 十、本次修复记录（两个缺陷）

v1.3.0 初次上线后，规则、开关、规则加载日志全部正常，但响应始终没有 `X-Cache`。定位到两处叠加的缺陷：

| # | 位置 | 缺陷 | 修复 |
|---|---|---|---|
| 1 | `internal/proxy/proxy.go`（`FlushInterval: -1`）＋ `internal/edge/accelerate.go` | 反向代理每写一段就调用 `Flush()`，而 `Flush` 无条件把缓冲刷出并切为透传，导致 `Close()` 里的缓存写入与压缩**永远不执行** | 新增 `flushGrace = 300ms`：宽限期内保持缓冲，超时才降级透传；SSE / 超限 / 非 200 仍即时透传 |
| 2 | `internal/edge/accelerate.go` | 上游带 `Content-Encoding` 直接透传。源站 Apache 默认 gzip，真实浏览器必然带 `Accept-Encoding: gzip`，于是缓存永远填不满 | 新增 `decodeEnc`：`gzip`/`br`/`deflate` 先解码为原始字节再入缓存，响应时按客户端能力重压；同时剔除带 `-gzip` 后缀的 `ETag` 与旧 `Content-Length` |

修复后的实测结果：

| 验证项 | 结果 |
|---|---|
| `/assets/*.js` 第二次请求 | `X-Cache: HIT`、`Content-Encoding: br` |
| 同一对象三种编码 | br / gzip / identity 均 `HIT`，体积递减 |
| 公网访问 | `HIT`、`Age` 递增，体积与源站 gzip 一致 |
| HTML 首页 TTFB | 约 24 ms，未劣化 |
| 进程内存 | 稳定在容量上限内 |

## 十一、排障对照表

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 规则保存了但从不命中 | 全局「启用」未开 | 打开总开关 |
| 只有部分静态资源命中 | 单对象上限太小（默认 2 MiB） | 调大「单对象上限」，并确认总容量够用 |
| 响应始终无 `X-Cache` | 源站发 `no-store` / `private` / `no-cache`，或带 `Set-Cookie` | 源站放开缓存头 |
| 改了文件内容但访问还是旧的 | TTL 未过期 | 手动清空缓存（可按前缀） |
| 命中率极低 | 前端给资源拼了时间戳参数（`?t=1710…`），每个 URL 都是新对象 | 改用内容指纹文件名 |
| 大文件不压缩也不缓存 | 超过单对象上限，直接透传 | 调大上限 |
| 登录用户看到别人的页面 | 用了后缀/前缀规则且未限制访客 | 改用「仅访客」或「目录匹配」 |
| `suffix` 写 `.css,.js` 无效 | 后缀匹配是单值字面量 | 拆成两条规则，或用正则 |
| 内存持续增长 | 总容量设置过大 | 下调「缓存总容量」，观察淘汰次数 |
| 缓存对象数突然掉到个位数 | 进程重启（热部署 / 崩溃 / OOM）会清空内存缓存 | 属预期行为，见第十二节 |

## 十二、缓存列表（页签）与「对象数变少」的排查

### 12.1 页签能看什么

`#/waf/cache` → **缓存列表** 页签，展示当前进程内存中的全部缓存对象，支持按站点过滤、按路径 / 文件名 / 域名搜索，以及分页。

| 列 | 数据来源 | 用途 |
|---|---|---|
| 文件名 | 路径最后一段 | 快速定位是哪个资源 |
| 路径 | 缓存键中的 `path?query` | 判断是否被 Query 拆成了多个对象 |
| 所属站点 | 缓存键第一段 | 多站点混跑时区分归属 |
| 域名 | 缓存键第二段（小写） | 同站点多域名时区分 |
| 大小 | 原始未压缩字节数 | 对照「单对象上限」 |
| 类型 | 响应 `Content-Type` | 判断是否被误缓存（如把 HTML 缓存了） |
| 命中次数 | 对象被读取的次数 | 找出「只写不读」的无效缓存 |
| 写入时间 / 过期时间 | `StoredAt` 与 `StoredAt + TTL` | 核对 TTL 是否按预期生效 |
| 剩余有效期 | 过期时间 − 当前时间 | 不足 5 分钟会标黄 |

接口：`GET /api/cache/entries?site=&keyword=&sort=storedAt|size|hits|expiresAt|remain&order=desc&page=1&size=20`，返回 `{list,total,entries,bytes}`；`entries` 是全量对象数，`total` 是过滤后的数量。

### 12.2 为什么设了 7200 秒，对象数还是很快变少

这是**内存缓存**，不是磁盘缓存。对象消失只有三种原因，按发生频率排列：

| 原因 | 判据 | 说明 |
|---|---|---|
| **进程重启** | 「淘汰次数」「清空次数」都是 0，且对象数在某个时间点整体归零 | 热部署、`systemctl restart`、崩溃、OOM 都会清空整块内存，与 TTL 无关 |
| 对象到期 | 列表里剩余有效期归零后消失 | TTL 7200 就是 2 小时后过期 |
| 被淘汰 / 被清空 | 「淘汰次数」或「清空次数」增加 | 总容量打满触发 LRU，或手动点了「清空缓存」 |

线上实测过一次：某次热部署在 6 分钟内重启了 3 次（16:45、16:48、16:51），控制台只剩 1 个对象，而 `evictions=0`、`purges=0`、`hits+misses` 仅 2 次。可见不是 TTL 提前过期，而是重启清空 + 该站点静态资源访问量本来就低（2 小时内只有 4 次 js 请求，其余全是扫描器打 `/.env`）。

**判断口径**：先看「淘汰次数」是否为 0、再看进程启动时间（`systemctl show -p ActiveEnterTimestamp --value gowaf`）。两者一对上，就无需怀疑 TTL。

### 12.3 需要「重启不丢」怎么办

当前版本没有磁盘缓存。若重启后不希望重新回源，可选：

1. 在 WAF 前面再加一层带磁盘缓存的 CDN/Nginx `proxy_cache`，由它承担持久层；
2. 重启后用脚本预热高频资源（`curl` 一遍首页引用的 `/assets/*`），把缓存重新填满；
3. 保持 TTL 较长（如 30 天）并让文件名带内容指纹，这样即使重启，回源一次后也能长期命中。
