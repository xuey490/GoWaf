# 检测引擎独立调用（模式 B）原理与部署决策记录

> 本文整理自 v1.6.0 发布后的两轮答疑，记录当时的结论与代码依据，供日后回溯。
> 关联文档：`docs/integrations-detect-api.md`（协议与集成）、`docs/v1.6.0-四项升级使用指南.md`（开启与验证）。
> 代码依据基于 v1.6.0（commit 21a32e5）：`internal/detectapi/server.go`、`internal/detect/exceptions.go`。

---

## 一、问题 1：开了 detect_listen，访客流量是不是就「直接通往 www.abc.com、不再经过 GoWAF」？

### 结论

**对一半。** `detect_listen`（如 `127.0.0.1:8020`）不是给访客流量用的口，而是给**网关来问话**用的口。

### 两种模式的完整图景

**模式 A —— GoWAF 接管 80/443（生产环境一直以来的样子，detect_listen 与此无关）**

```
访客 → GoWAF(80/443) → 检测 → 转发 → 后端 8080
```

GoWAF 自己是门卫+转发员：流量必须穿过它，检测完顺手送进后端。站点列表里的上游/负载均衡配置在这条链路上生效。

**模式 B —— detect_listen 的用途（网关继续看门，GoWAF 变「传达室」）**

```
访客 → Nginx/Traefik(80/443) ──逐请求问 GoWAF:8020「放不放行？」
                             ← 回答：放行 / 403 / 需人机校验
       Nginx 根据答复转发 → 后端 8080
```

GoWAF 从「门卫」退到「传达室」：**只有问话进来（8020），访客流量不经过它**。检测还是它做，但转发归 Nginx 管。

### 关键认知：访客流量不是「直通后端」

模式 B 里访客流量通往**另一个看门的网关**（Nginx/Traefik/Kong），而这个网关必须**每个请求都问一次 GoWAF**——不问就没有任何防护。问话环节不是自动的，必须给网关配接入：

- Nginx/OpenResty：`deploy/integrations/nginx/waf_detect.lua` + `nginx.conf.example`（auth_request）
- Traefik：`deploy/integrations/traefik/forwardauth.yml`（forwardAuth）
- 网关拿到答复：2xx 转发 / 403 拦截 / 401 引导到人机校验页

### 选型速查

| 场景 | 选择 |
|---|---|
| GoWAF 直接接管 80/443（当前生产方式） | 模式 A，不配 8020 |
| 已有 Nginx/Traefik 体系不想换网关，只想加 WAF 检测能力 | 模式 B，网关配好问话，8020 只监听回环/内网 |
| 网关机与 WAF 机分两台 | 模式 B 变体：`detect_listen: "0.0.0.0:8020"` 且**必须配 detect_token** |

一句话：**8020 是「问话窗口」，不是「流量入口」。** 开了它 GoWAF 不会自动失去流量；只有主动把网关切换成模式 B，流量才从 GoWAF 手里移交给 Nginx——而防护依然在 GoWAF 手里，只是从「直接拦截」变成「给网关回话」。

## 二、问题 2：模式 B 算不算「旁路监听」？

### 结论

**不算。** 模式 B 是**同步串行问询**，不是旁路镜像。

### 区别在哪

| | 旁路监听（镜像/IDS 式） | 模式 B（GoWAF 的 /check /detect） |
|---|---|---|
| 流量方向 | 复制一份给分析器，主流程照常 | 网关**阻塞等待** GoWAF 答复才转发 |
| 时效 | 异步，事后分析 | 同步，请求级实时 |
| 拦截能力 | 不能拦（只能报警） | **能拦**——答复 403 的请求根本到不了后端 |
| 分析器挂了 | 主流程无感 | 网关必须抉择放行/拒绝（fail-open/fail-closed 由网关侧配置） |

所以模式 B 的准确描述是：**把「转发」和「判定」解耦成两个进程的分离式部署；判定环节本身仍是串行在线（in-line）的**。防护语义与模式 A 等价：该拦的照样拦，只是执行者从 GoWAF 换成了网关。

## 三、问题 3：切模式 B 后，站点列表里的 www.abc.com 要移除还是保留？

### 结论

**保留，不要移除。** 站点列表相当于「资产台账」，留着只有好处、没有坏处。

### 保留的四个理由

1. **例外规则依赖站点名**（最关键）：例外规则按「站点名+路径」匹配。`/detect` 协议带 `site` 字段，网关传入站点名后，站点级例外（如 `sem-ssti` 在某站放行）才会生效。依据：`internal/detectapi/server.go` 的 `inspect()` 把 `site` 传给 `detect.Input.Site`，再经 `engine.FilterByException(res, site, path, params)` 匹配。
2. **事件库按站点归类**：命中记录继续挂在站点名下，统计、检索、告警不乱。
3. **支持混合过渡**：部分站点走模式 A、部分走模式 B 完全可行，站点列表两种都要登记。
4. **对检测 API 无害**：`/detect`、`/check` 的判定**不使用**站点条目里的上游/代理配置，站点留在列表里不会产生任何转发动作。

### 但有三个真实的坑（当时明确记录）

1. **动作判定降级为全局口径**：模式 B 用全局阈值与模式，控制台里**站点级** guard 覆盖（站点级挑战阈值/封禁策略）不生效。依据：`docs/integrations-detect-api.md` 差异表「动作判定：站点级 guard 覆盖 → 全局阈值与模式」。
2. **`/check` 端点不传站点名**：代码里 `handleCheck` 调用 `s.inspect(method, host, path, query, "", headerText, "")`——site 为空串，站点级例外在 `/check` 链路匹配不上，只有全局例外生效。需要站点级例外时让网关走 `/detect` 并带 `site` 字段（nginx lua 集成可配置）。依据：`internal/detectapi/server.go` handleCheck 尾部。
3. **完全切模式 B 的前提**：GoWAF 必须让出 80/443（改数据面监听配置），否则端口冲突 Nginx 绑不上。站点条目留着没问题——GoWAF 是否占 80/443 由监听配置决定，与站点列表互不影响。

## 四、当时的一页速记

> **模式 B = 门卫换人、安检外包**：Nginx 管放行，GoWAF 管判定，请求照样一个个过安检门（串行问询），不是旁观录像（旁路）。
> **8020 是问话窗口，不是流量入口。**
> **站点列表当成资产台账继续登记**：例外规则、事件归类、混合部署都靠它；唯一记得住的是——模式 B 判定走全局口径，站点级例外要用 /detect + site 才生效。
