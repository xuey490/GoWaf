# 检测前多层解码（engine.decode）设置指南

> 适用版本：v1.5.0+ · 所属模块：检测引擎增强 · 控制台入口：**防护配置**

## 一、这是什么

在规则/语义检测之前，对请求中的**编码绕过面**做解码，把"检测器看不懂原文"的攻击载荷还原出来再检测。覆盖三类绕过：

| 绕过面 | 例子 | 原文样子 |
|---|---|---|
| **base64 编码** | payload 整体 base64 | `?token=MScgT1IgJzEnPScx` |
| **压缩请求体** | API 客户端/脚本带 gzip 的 body | 二进制压缩流，任何正则都扫不到 |
| **Unicode 转义** | JSON 体内的 `\u0027` | `{"q":"1\u0027 OR ..."}`，原文看不见引号 |

> 说明：**多层 URL 解码、HTML 实体、全角字符、SQL 注释**这些绕过早已由引擎的归一化层（Normalize）覆盖，本功能不重复处理；这里补的是归一化覆盖不到的三类。

对应雷池（SafeLine）语义引擎"天然免疫变形 payload"能力中，开源可落地的部分。

## 二、工作原理

```
请求（query / body）
  → 快速特征检查（base64 字符集+长度 / 压缩魔数 / 含 \u）
  → 解码：base64（最多 max_depth 层）、gzip/deflate/zlib 解压、\uXXXX 还原
  → 生成「解码变体」（不替换原文，附加检测文本）
  → 自研规则引擎 + libinjection 语义通道 同时扫描 原文 + 变体
  → 同一规则跨原文/变体只记一次命中，分数不会翻倍
```

关键设计：

1. **变体附加而非替换**：原文照常检测，变体是额外的扫描文本；事件里的证据能看出命中来自哪一层；
2. **CRS 不吃变体**：Coraza 自带 `t:urlDecode`/`t:base64Decode` 变换链，再喂变体会双重解码；变体只喂自研引擎与 libinjection；
3. **防御性约束（防 DoS）**：只在快速特征检查通过时才尝试解码；单变体字节上限 `max_bytes`；base64 层数上限 `max_depth`；解码失败静默放弃（少一个变体不会漏检原文）；
4. **默认开启**：URL 多层解码本就由归一化层处理，这里补的三类绕过面成本有界、收益直接。

## 三、控制台配置步骤

进入 **防护配置 → 引擎加固与语义检测** 分组（本功能在同一分组下方「检测前多层解码」）：

| 设置键 | 说明 | 默认值 | 取值 |
|---|---|---|---|
| `engine.decode.enabled` | 总开关 | `true` | true/false |
| `engine.decode.max_depth` | base64 最大解层层深 | `2` | 1~3 |
| `engine.decode.max_bytes` | 单变体字节上限 | `65536`（64KB） | ≥1024 |

保存即热生效，无需重启。

## 四、效果验证

**base64 载荷**（默认应被语义通道识别为 SQLi）：

```bash
# base64("1' OR '1'='1") = MScgT1IgJzEnPScx
curl "https://your-site/search?token=MScgT1IgJzEnPScx"
# 事件页：libi-sqli 命中（语义通道扫到了解码变体）
```

**unicode 转义载荷**：

```bash
curl -X POST https://your-site/api/query \
  -H "Content-Type: application/json" \
  -d '{"q":"1\u0027 OR \u00271\u0027=\u00271"}'
```

**gzip 压缩体**：

```bash
curl -X POST https://your-site/api/submit \
  -H "Content-Encoding: gzip" \
  --data-binary @payload.gz
```

三条都会在「攻击事件」里产生带归因的事件；把 `engine.decode.enabled` 关掉再发一遍，前两条的 libi 命中将消失（对照组）。

## 五、设计边界

1. **层数上限是 3**（配置 1~3）：更深的编码在真实攻击里几乎不存在，而在 DoS 视角是指数放大器；
2. **64KB 变体上限**：解出超大内容时截断——攻击特征几乎都在前几 KB；
3. **plausibility 检查**：base64 解出的内容必须通过 UTF-8 合法性与可打印比例（≥80%）检查，解出纯随机字节的"伪 base64"直接放弃，不产生垃圾变体；
4. **query 按参数值解码**：RawQuery 里通常只有个别参数是 base64（如 `?token=xxx`），按 `&` 分段对每个值尝试，变体保留 `k=decoded` 形式（事件证据可读）；body 支持整段 base64 与压缩体；
5. **变体不进 CRS**：Coraza 的变换链已覆盖 URL/base64 解码，重复喂会双重解码产生误报。

## 六、注意事项

1. **默认开启，一般不用动**：只有在排查"解码导致的误报"或极端性能场景才关闭/收紧；
2. **性能画像**：特征检查不通过时接近零成本；通过时一次 base64 解码是 O(n) 内存拷贝，64KB 上限内微秒级；gzip 解压是最贵的路径（约每 100KB 毫秒级），大 body 场景可把 `max_bytes` 调小；
3. **误报治理**：解码变体走与原文相同的例外规则体系（按站点/规则 ID/分类/参数名），标记误报后变体命中同样被豁免；
4. **与 libinjection 的关系**：语义通道是变体的最大受益者——base64 之后的变形 payload 正则可能追不到，但词法指纹仍然成立；
5. **观察解码是否在工作**：事件详情里命中目标（Target）仍显示 query/body，证据片段会包含解码后的文本；指标 `waf_rule_hits_total` 中带 `libi-` 前缀的规则命中数应明显上升（对比关闭状态）。

## 七、常见问题

**Q：会不会把正常 base64（图片、JWT）误判成攻击？**
不会"判"——解码只是生成附加检测文本，最终拦截仍走评分与阈值。正常图片/JWT 解出的内容不含攻击特征，不产生分数。JWT 本身由响应侧敏感信息过滤负责（resp-jwt），与这里无关。

**Q：双层 base64 能解吗？**
能，`max_depth=2` 支持 base64 of base64；第 3 层需要显式调到 3（不建议，误报面与成本都会上升）。

**Q：请求体是 zip/brotli 呢？**
不支持。gzip/deflate/zlib 之外的主流场景是 multipart 上传（走上传检测）与 br（浏览器不用于请求体）。有需求再扩展。
