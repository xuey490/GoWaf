# 网页防篡改（tamper）设置指南

> 适用版本：v1.5.0+ · 所属模块：响应侧防护 · 控制台入口：**防护配置**

## 一、这是什么

对指定的页面/静态资源做**完整性防护**：管理员生成「可信基线」后，WAF 对每个经过的响应与基线比对——

- **observe 模式**（默认）：内容与基线不一致时只记录事件（规则 ID `tamper`），内容原样下发——先观察覆盖面与误报；
- **block 模式**：不一致时**用基线副本替换响应**，访客拿到的是可信内容，被篡改的版本出不了 WAF，同时记录事件。

对抗场景：上游应用/主机被入侵后页面被挂马、插暗链、改标题——请求侧检测拦不住"上游自己吐出被改的内容"，防篡改是最后一条防线。对应雷池（SafeLine）的「静态防护」能力。

## 二、工作原理

```
【基线生成（手动）】管理员点击「重新生成基线」
    → WAF 对每个启用站点 × 每个受保护路径回源抓取响应
    → 记录 SHA-256 哈希 + 内容副本（≤ max_bytes，总量 ≤ 64MB）

【运行期比对】响应（200 且类型在保护范围）→ 与基线哈希比对
    → 一致   → 放行
    → 不一致 → observe: 记录事件(tamper)，原样下发
              block:   用基线副本替换响应 + 记录事件(tamper)
```

关键设计（与文件级防篡改的差异，请务必理解）：

1. **基线来自回源抓取，可信度 = 生成基线那一刻的内容状态**。因此基线**只支持手动刷新**，绝不定时自动重抓——定时重抓会在内容已被篡改后把篡改版固化成新基线；
2. **基线存内存**：进程重启后基线失效，需要重新生成（生成前的空窗期不比对、不拦截，行为等同未开启）；
3. **没有基线就不比对**：不会把"第一次见到的内容"当成可信内容；
4. **受保护路径自动跳过页面缓存**：缓存 HIT 会绕过比对阶段，宁可放弃加速；
5. **只比对 200 响应**且 Content-Type 属于保护范围（HTML/文本/CSS/JS/JSON/XML/图片/字体）。

## 三、控制台配置步骤

1. 进入 **防护配置**，找到「网页防篡改」分组：
   - **启用防篡改**：`true`；
   - **比对模式**：`observe`（先观察）或 `block`（替换为基线副本）；
   - **受保护路径**：逗号分隔的**精确路径**，如 `/index.html,/logo.png,/static/app.js`；
   - **单副本上限**（字节）：默认 1048576（1MB）；
   - 保存；
2. 点击「重新生成基线」（带确认弹窗），等待逐项结果：
   - 成功：显示站点、路径、哈希、大小；
   - 失败（上游不可达/非 200/超上限）：显示原因，**旧基线保留**；
3. 观察一段时间（事件页按分类 `tamper` 检索），确认无误报后切到 `block` 模式。

## 四、API 配置示例

开启并配置受保护路径：

```bash
curl -X PUT http://127.0.0.1:8899/api/settings \
  -H "Authorization: <access token>" -H "Content-Type: application/json" \
  -d '{
    "tamper.enabled": "true",
    "tamper.mode": "observe",
    "tamper.paths": "/index.html,/logo.png,/static/app.js",
    "tamper.max_bytes": "1048576"
  }'
```

生成基线（对每个启用站点 × 每条路径回源抓取）：

```bash
curl -X POST http://127.0.0.1:8899/api/tamper/refresh \
  -H "Authorization: <access token>"
# → {"items":[{"site":"官网","path":"/index.html","ok":true,"sha256":"…","size":15320}, …]}
```

查看基线状态：

```bash
curl http://127.0.0.1:8899/api/tamper/status -H "Authorization: <access token>"
```

## 五、配置项说明

| 设置键 | 说明 | 取值 |
|---|---|---|
| `tamper.enabled` | 总开关 | true/false，默认 false |
| `tamper.mode` | 比对模式 | `observe` 只记录 / `block` 替换为基线副本 |
| `tamper.paths` | 受保护路径（**精确匹配**，逗号分隔） | 每条 ≤255 字符，最多 256 条 |
| `tamper.max_bytes` | 单个基线副本上限（字节） | 默认 1048576；超过的路径只比对哈希、无法替换 |

## 六、注意事项

1. **路径是精确匹配**：写 `/index.html` 只保护这一个 URL，不保护 `/article/index.html`。要保护多个页面就列全，或挑最关键的首页/落地页；
2. **动态页面慎用**：页面内容随时间变化的（实时数据、CSRF token 随机化）会产生持续误报——防篡改适合**内容稳定**的页面与静态资源；
3. **基线更新纪律**：站点正常改版后必须手动刷新基线，否则改版内容会被当成"篡改"（block 模式下访客拿到的永远是旧版页面）；
4. **重启后基线失效**：进程重启 → 基线清空 → 比对暂停（不拦截），重新点击生成即可；
5. **block 模式的替换边界**：响应超过 `max_bytes` 时只记录无法替换（没有副本可回退）；
6. **指标**：`waf_tamper_hits_total{site,outcome}`，outcome ∈ match / mismatch / replaced；
7. **先 observe 后 block**：这是本功能的使用纪律——observe 看一周误报，再切 block。

## 七、常见问题

**Q：站点改版了，页面被 block 模式"还原"成旧版怎么办？**
立即在设置里把模式切回 observe（或关闭开关）→ 修复/确认新内容正常 → 重新生成基线 → 切回 block。

**Q：为什么不自动定期刷新基线？**
自动重抓 = 把"当前内容"无条件当可信内容。一旦内容已被篡改，重抓反而把篡改版固化为新基线，防护静默失效。手动刷新是刻意的安全设计。

**Q：能保护整站吗？**
不建议。256 条上限 + 内存副本预算（64MB）决定了它适合保护"关键少数"（首页、落地页、核心静态资源）。整站完整性请配合源站层面的文件校验（如 AIDE）。

**Q：与页面缓存冲突吗？**
不冲突——受保护路径会自动跳过缓存，每个响应都走实时比对。代价是这些路径失去加速。
