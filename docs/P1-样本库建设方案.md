# P1 第 1 项建设方案：语义广度 20+ 类 + ≥10K 样本库跑分

> 目标口径（《v1.6.0-与雷池社区版对比》）：检测类别扩到 20+，自建 ≥10K 样本库（含变形），
> 检出率 ≥70%，误报率 ≤0.1%，数据公开。

## 一、现状盘点（起点）

| 通道 | 已覆盖类别 |
|---|---|
| libinjection（libi.go） | SQLi、XSS（2 类，成熟） |
| 语义通道（semantic.go） | cmdi、rce、xxe、ssrf、ssti、expr、deser（7 类） |
| CRS（crs.go） | 泛特征覆盖（不计入语义类目，但参与跑分） |

距离 20+ 还差约 11~13 类。**关键认知：类别扩张与样本库建设必须交替进行**——
每新增一类，先写判定式，再用样本库跑分验证该类召回，再修误报，滚动推进。

## 二、类别扩张路线（7 → 20+）

按「结构特征可判定 + 误报可控」优先级排序，分两批：

**第一批（结构特征清晰，判定式成熟度高）：**
1. `traver` 路径穿越（`../` 变体、绝对路径探测 /etc/passwd、C:\windows）
2. `lfi` 文件包含（php://filter、data://、zip:// 等 wrapper）
3. `nosqli` NoSQL 注入（`$ne`/$where/$regex + MongoDB 语法结构）
4. `ldapi` LDAP 注入（`)(` 闭合 + filter 结构，如 `*)(uid=*))`）
5. `xpati` XPath 注入（`]' or 'a'='` 类闭合结构）
6. `crlf` CRLF/日志注入（header 拆分、日志换行注入）
7. `openredirect` 开放重定向（scheme 切换 + 域名跳板结构）
8. `prototype` 原型链污染（`__proto__`/`constructor.prototype` 链式赋值）
9. `smugg` HTTP 走私特征（TE/CL 冲突头组合——走 header 判定）

**第二批（对抗性强或误报风险高，谨慎低分）：**
10. `webshell` Webshell 上传/调用特征（eval/assert/base64 链 + 可变变量）
11. `graphqli` GraphQL 攻击（内省批量查询、别名轰炸结构）
12. `prompt` LLM 提示注入（指令覆盖结构：忽略上文/泄露 system prompt 模板）
13. `xsleak`/`xslt` 视误报验证情况决定是否收编

**总分口径**：每类沿用现行策略——单类命中分 < 拦截阈值(60)、≥ 挑战阈值(30)，
误报代价是人机校验而非 403，这是 0.1% 误报目标能达成的结构性前提。
跑分时「检出」定义为分数 ≥ 挑战阈值（即引擎产生拦截/挑战事件）。

## 三、样本库建设（≥10K，公开可复现）

### 3.1 目录与格式

```
testdata/bench/
├── attacks/<category>/xxx.txt      # 一文件一原始 HTTP 请求（含头+体）
├── benign/xxx.txt                  # 良性请求
├── manifest.jsonl                  # {file, label, category, source, license}
└── tools/bench/                    # 跑分器（Go，复用 detect.Engine）
```

原始 HTTP 请求文本格式（与 go-ftw 一致）可直接 `http.ReadRequest` 回放，
保证「样本 = 真实线格式」而非拼凑字符串。

### 3.2 攻击样本来源（种子，预计去重后 1.5K~2.5K）

| 来源 | 规模 | 许可 | 用法 |
|---|---|---|---|
| PayloadsAllTheThings | 数千 payload | MIT | 逐类抽取，包裹成 HTTP 请求 |
| SecLists（Fuzzing/SQLi/XSS 等） | 数千 | 与源一致（多为 MIT/CC0） | 同上 |
| CRS 官方回归测试（coreruleset，go-ftw YAML） | ~700 用例 | Apache-2.0 | 直接转 HTTP 请求 |
| ModSecurity 测试套件 | 数百 | Apache-2.0 | 同上 |
| waf-bypass 类项目 payload | 数百 | 各异，逐仓核实 | 变形种子 |

**许可纪律**：manifest.jsonl 逐条记录 source 与 license；许可不明或禁止再分发的
只入变形规则不直接入库。

### 3.3 良性样本来源（≥10K，误报分母）

| 来源 | 说明 |
|---|---|
| CSIC 2010 HTTP 数据集 | 学术经典，~62K 条真实 HTTP（含少量攻击，需按 manifest 剔除攻击标签部分只用 normal 子集） |
| 自有生产流量脱敏 | 导出真实 GET/POST（脱敏 Cookie/表单值），最贴近误报实况 |
| 常见框架正常 URL 生成器 | WordPress/Django/Spring/Jenkins/GitLab 典型路径+参数脚本生成 |
| base64/JWT/JSON 正常载荷 | 富编码内容是语义引擎最大的误报风险源，必须足量 |

### 3.4 变形生成（1.5K 种子 → 10K+ 的关键）

写一个变形器（Go，`tools/bench/mutate.go`），对种子 payload 施加**组合变换**：

- 编码类：单次/双次 URL 编码、HTML 实体（命名/十进制/十六进制）、Unicode 转义、
  全角字符、Base64（针对有解码通道的类别）
- 语法类：大小写交错、插入 SQL/JS 注释（`/**/`、`<!--`）、空白变体（%09/%0a/+）
- 结构类：参数位置轮换（query ↔ body ↔ UA）、等价 payload 替换（cat→head/tail）

每种变换是确定性函数，种子 × 变换 × 位置 ≈ 每种子 6~10 个变体，
2K 种子即可稳定产出 12K+ 攻击样本。**变形后必须复跑引擎验证标签不变**
（变形把攻击变成「检测不到的攻击」没有跑分意义，除非单独归为 bypass 用例）。

### 3.5 跑分器（tools/bench）

```
wafbench -dir testdata/bench -threshold 30 -report report.json
```

- 遍历样本 → `http.ReadRequest` → 走与线上一致的 Normalize + libi + semantic + CRS 管线
- 输出：总检出率、逐类召回率、误报数/误报率、每条失败样本明细（做成回归清单）
- report.json 提交进仓库，任何人 clone 后 `go run ./tools/bench` 可复现同一数字

### 3.6 数据公开方式

- 样本库 + 变形器 + 跑分器 + 生成文档全部入仓库（独立 `bench` 目录）
- README 记录每个外部来源的 commit/版本号，保证第三方复现时取到同一批数据
- 敏感样本（脱敏后的生产流量）只入库脱敏版本，或以生成脚本形式公开（脚本公开、原始数据不入库）

## 四、里程碑

| 阶段 | 内容 | 交付物 |
|---|---|---|
| M1 | 跑分器 + 变形器框架 + 首批外部种子入库（约 5K 样本） | 基线报告（明确现有引擎真实召回/误报） |
| M2 | 第一批 9 类判定式 + 逐类样本补齐 | 类别 16，报告迭代 |
| M3 | 第二批类别 + 良性库扩到 10K | 类别 20+，全量报告 |
| M4 | 失败样本回归清单 → 判定式调优，锁定 ≥70% / ≤0.1% | 公开基线 report.json |

工作量提示：M1~M2 是大头（判定式写作 + 逐类误报治理），M3/M4 主要是数据工程。
最大风险不在「凑够 10K」（变形器可机械放大），而在**良性库的代表性**——
误报 0.1% 意味着 10K 良性样本最多错 10 条，现有语义通道的富编码误报
（Base64/长 token 串）大概率会先击穿这个数字，M1 基线报告要第一个看它。
